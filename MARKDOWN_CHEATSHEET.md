# Markdown Cheatsheet — Make Your Docs Look Professional

Everything below is rendered by GitHub, GitLab, VS Code preview, and most platforms.

## 1. Headings — structure your document

```markdown
# H1 (only one per document, use it as the title)
## H2 — main sections
### H3 — subsections
#### H4 — rarely needed
```

- Use exactly **one H1** (the page title). Everything else should be H2 and below.
- Headings should describe a *section*, not a sentence. Keep them short.
- Do not skip levels (H2 → H4 jumps are messy).

## 2. Emphasis — make text stand out

```markdown
*italic* or _italic_
**bold** or __bold__
**_bold italic_**
~~strikethrough~~
`inline code` for names, keys, and short commands
```

Use bold for *key terms*, italic for *emphasis or titles*, and inline code for *anything the reader might type*.

## 3. Lists — keep it scannable

```markdown
- bullet point
- another bullet
  - nested bullet (indent 2 spaces)

1. first step
2. second step
3. third step
```

Rules for professional docs:
- Same type per level (don't mix `-` and `*`).
- End items with a period only if they are full sentences.
- Use numbered lists **only** for steps that must happen in order.

## 4. Links and images

```markdown
[link text](https://example.com)
[link to file](./chapter2.md)      # relative link within the repo
![alt text](./images/diagram.png)  # image
![alt text](image.png "optional title")
```

- Link text must describe where the link goes, never "click here".
- Always add alt text to images (accessibility + shows if image is broken).
- Store images in an `images/` folder and link relatively.

## 6. Tables — present data cleanly

```markdown
| Feature    | Supported | Notes                     |
| ---------- | :-------: | ------------------------- |
| Headings   |    Yes    | Great for structure       |
| Tables     |    Yes    | Use for comparison        |
| Emoji      |   Maybe   | Depends on the platform   |
```

Column alignment with colons in the separator row:
- `:---`  left-align
- `:---:` center-align
- `---:`  right-align

Tables work best for *comparisons*; use lists for simple enumerations.

## 7. Blockquotes — highlight notes and warnings

```markdown
> This is a plain note.

> [!TIP]
> GitLab/VS Code style callout. Supported by some platforms.

> [!WARNING]
> Don't do the thing this warning describes.
```

Tip: put "Note:" / "Tip:" / "Warning:" at the start so it reads clearly even where callouts aren't supported.

## 8. Horizontal rules — separate sections

```markdown
---

Use them sparingly. Headings usually do the job better.
```

## 9. Task lists — track progress

```markdown
- [x] Finished task
- [ ] Pending task
```

Great for checklists, practice plans, and release notes.

## 10. Escaping special characters

If you need a literal `#`, `*`, or other markdown character, escape with a backslash:

```markdown
\# not a heading
\*literal asterisk\*
```

## 11. Structural rules for professional-looking docs

1. **Start with a title + one-sentence intro.** Readers decide instantly whether to continue.
2. **Use a table of contents** in long documents (auto-generated by GitHub when you add enough H2s, or link headings manually).
3. **Keep paragraphs short** (2–4 sentences). Walls of text get skimmed.
4. **One idea per line in lists.** Start each bullet with a verb where possible.
5. **Use relative links** so your repo stays portable.
6. **Add a footer** with license or links: `See [LICENSE](./LICENSE)`.
7. **Preview before committing** (VS Code: `Ctrl+Shift+V`).
